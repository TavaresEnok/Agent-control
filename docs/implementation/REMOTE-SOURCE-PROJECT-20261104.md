# Origem SSH vinculada ao repositório do projeto — 04/11/2026

Fatia de RF-51/T25. O snapshot Git já exportado, verificado e autorizado para o mesmo projeto, host, commit e tree pode virar o repositório local de trabalho do projeto. A operação é `project.materializeRemoteSource` em `ProjectAdmin.execute`, o mesmo caminho assinado de `project.register`. O titular precisa ser administrador global e owner do projeto. `intentId` e `deliveryAttemptId` seguem o replay existente: a mesma intenção devolve o resultado gravado; outra carga com a mesma intenção é `PROJECT_ADMIN_INTENT_CONFLICT`.

O pedido não traz caminho, comando nem raiz. A raiz é a de menor `id` já configurada no controlador. O caminho relativo é `remote-sources/<projectId>`. O bundle vai no comando, em base64, e o SHA-256 tem de ser o do recibo `git-export`. O corpo HTTP de project-admin permanece em 16384 bytes; um bundle real pode não caber nessa rota. Os testes chamam `ProjectAdmin.execute` direto. O limite não foi aumentado.

## Proveniência

A migração aditiva 059 cria `ac_remote_source_materializations`, schema 1, imutável. A linha guarda projeto, contexto, host, operação, commit, tree, SHA-256 do bundle, autorização usada, principal e instante. Ela entra na mesma transação que o repositório, `ac_project_repository_identity`, a intenção administrativa e a auditoria `project.remote_source.materialized`. O snapshot continua `not_reviewed`. Não nasce artefato e não libera integração.

## Recusas

Autorização ausente: `REMOTE_SOURCE_AUTHORIZATION_REQUIRED`. Assinatura ou autorização ilegível: `OPERATOR_SIGNATURE_INVALID` ou `REMOTE_SOURCE_AUTHORIZATION_INVALID`. Quem não é admin global recebe `CONTROL_ADMIN_REQUIRED`; admin que não é owner recebe `PROJECT_OWNER_REQUIRED`. Projeto, host, commit, tree ou digest diferentes do recibo: `REMOTE_SOURCE_IDENTITY_MISMATCH`. Projeto que já tem repositório ou identidade: `PROJECT_REPOSITORY_ALREADY_BOUND`. Destino publicado com outro commit, tree suja ou que não é um diretório Git: `REMOTE_SOURCE_DESTINATION_CONFLICT`; esse caminho não é apagado. Bundle acima de 65536 bytes: `REMOTE_SOURCE_BUNDLE_TOO_LARGE`. Raiz que não é canônica, não pertence ao processo ou é gravável pelo grupo: `PROJECT_ROOT_UNAVAILABLE`. O diretório privado pode ficar dentro da raiz confiável, como no `project.register`. Só o work tree `remote-sources/<projectId>` e o staging `.remote-source-staging/<intentId>` conflitam com ele (`PROJECT_PRIVATE_DIRECTORY_CONFLICT`). A raiz inteira não é recusada por conter o diretório privado.

## Contenção antes de efeito

Antes de qualquer `rm`, escrita, `clone`, `chmod` ou `rename`, a operação classifica com `lstat` os pais `.remote-source-locks`, `.remote-source-staging` e `remote-sources`, e as folhas do projeto e da intenção. Symlink, arquivo, dono diferente do processo, escrita de grupo ou de outros, ou caminho não canônico é `PROJECT_PATH_FORBIDDEN`. A recusa não altera modo, não segue symlink e não apaga a folha. Diretório ausente é criado com `0700` (locks e staging) ou `0755` (`remote-sources`), um nível por vez, sem `mkdir` recursivo. Diretório existente inseguro não é reparado com `chmod`. O `chmod` do clone novo usa descritor aberto com `O_NOFOLLOW`. O scratch tmpfs inseguro também é recusado, sem `chmod` de correção.

## Concorrência e crash

O diretório de trabalho é publicado antes da transação. Repositório, identidade e proveniência só commitam juntos. A exclusão entre processos é `pg_try_advisory_lock(hashtextextended(projectId, 59))` numa sessão segurada até o fim. PostgreSQL solta esse lock quando a sessão morre, inclusive por `SIGKILL`, sem depender de `finally`. O arquivo `owner` guarda `intentId`, `pid` e `token`, e é publicado por `rename`. Só o token detentor apaga o diretório do lock. Dono ausente, vazio ou JSON sem os três campos é criação interrompida: sob o lock da sessão o diretório é refeito e não fica `BUSY` para sempre. Pid morto da mesma intenção permite retomar; a árvore já publicada com o mesmo commit, o mesmo tree e work tree limpo é adotada e não é substituída. Outra intenção, com pid morto ou vivo, recebe `REMOTE_SOURCE_MATERIALIZATION_BUSY` e o `owner` dela permanece. Duas materializações vivas: uma segue; a outra recebe busy. A prova de morte é um processo filho terminado com `SIGKILL` depois do rename e antes do registro; duas retomadas concorrentes precisam deixar uma posse, um vínculo e uma proveniência. O gancho `beforeRemoteSourceRegister` continua só no teste em processo e não é a prova de crash. O servidor não configura esse gancho.

O scratch bare fica em tmpfs, por padrão `/dev/shm/agent-control-remote-source`, e passa pelo `RemoteGitMaterializer`. O checkout para a raiz confiável usa `git clone --no-hardlinks -b agent-control-export`. Não há CLI nem login de IA no destino. O worker remoto não mudou.

## Leitura

`ProjectAdmin.view` acrescenta `remoteSources` só para os projetos do principal: host, commit, tree, estado `materialized` e revisão `not_reviewed`. Não devolve bundle, chave, prova, caminho nem hostname. O painel existente mostra isso em texto. Não há botão de materializar. Resposta antiga sem o campo continua válida.
