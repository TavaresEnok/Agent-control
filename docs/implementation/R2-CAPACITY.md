# Capacity queue and selection evidence

The PostgreSQL capacity lock serializes admissions across clients. Eligible waits retain their existing manager/evaluation/programmer priority for five minutes. After five minutes, database-created wait age promotes them ahead of younger waits; promoted waits are ordered by their persistent sequence. Retry updates do not reset age or sequence. This bounds priority overtaking while an eligible waiter remains present, provided capacity is released and callers retry; no scheduler or preemption is introduced. Paused, archived, canceled, expired-authority, inaccessible, or otherwise ineligible waits are excluded by the existing admission query. Existing account, role, global, original-reserve and context limits still apply.

Each new model grant records the chosen account and profile, policy and capacity configuration revisions, regular/emergency chain, one-based position in the effective sticky-first chain, and a safe reason (`sticky`, `first_eligible`, or `fallback`). The authorized context control view exposes this evidence with the grant. Older and local-compositor grants have null evidence. Policy verification hashes the stored snapshot itself before using its parsed form, preserving historical snapshots that omitted optional defaulted fields.

Verification: TypeScript typecheck and focused disposable-PostgreSQL tests. The aging test advances only a server-owned fixture row rather than accepting a client timestamp; it covers concurrent clients, initial priority, promotion, releases and paused contexts. Existing liveness tests exercise sticky, emergency, evaluation and reserve behavior.
