# R4 — entrada da conversa e configuração assinada

A entrada canônica Happier continua usando a origem confiável de build e o menu existente. A rota explícita `/settings/agent-control?acSession=...` agora alcança o resolvedor autenticado antes do redirecionamento legado ao projeto padrão. O resolvedor consulta o gateway global; um vínculo autorizado leva à rota do projeto correspondente, nenhum vínculo oferece formulário de configuração e múltiplos vínculos exigem escolha humana. O painel com projeto continua preso ao `session_id` solicitado. O gateway é a autoridade de acesso; o cliente não usa metadata ou texto do modelo para escolher projeto ou contexto.

O banco hoje impõe unicidade de sessão; a escolha de múltiplos resultados é uma guarda para compatibilidade futura, coberta por teste de interface. O lookup não cadastra projeto nem cria vínculo. Sessões sem vínculo precisam ser vinculadas previamente pelo fluxo normal de projeto.

O runner `scripts/r4-ui-conversation-browser.mjs` usa PostgreSQL novo, Happier light real, `server-main` real e o SPA administrado. O projeto vinculado difere deliberadamente do projeto padrão. O preparo autentica conta sintética no Happier por desafio assinado, emite o cookie HttpOnly pela rota de produto, vincula a conversa e inscreve o dispositivo pelo formulário. A etapa composta exporta o código corrente do Happier, abre a conversa, clica seu menu real e espera o painel fixado no projeto/conversa. Em seguida publica uma política assinada (limite de programadores 2), confere a revisão 2 no PostgreSQL, recusa o mesmo contrato sem prova humana com origem correta e código `HUMAN_CONTROL_AUTH_REQUIRED`, e pausa/recarrega o contexto.

Preparação: Node 22.23.3, dependências locais já disponíveis, PostgreSQL `postgres:16-alpine`, Chrome e links reversíveis do helper `link-happier-test-deps.mjs`. O SPA deve ser compilado com `VITE_AGENT_CONTROL_MANAGED=1 npm run build --prefix upstream/cezar/packages/web`, usando destino `web/dist` próprio (nunca link para um destino compartilhado). `npm run build` prepara os overlays runtime Cezar. `AC_R4_CONVERSATION_EXPORT_DIR=/caminho/novo` preserva a exportação canônica e um manifesto com SHA-256 de todos os arquivos, árvore Git Happier, commit e origens loopback. A reexecução independente usa `AC_R4_CONVERSATION_BUILD_DIR=/mesmo/caminho`; o runner reserva as portas declaradas e o helper confere todos os hashes, a árvore Happier corrente e ausência de alterações rastreadas nesse subtree. Cada execução cria conta, banco, conversa e navegador novos; o export não contém credenciais.

O override Metro pertence somente à bancada, pelo mecanismo suportado `EXPO_OVERRIDE_METRO_CONFIG`. Ele mantém o resolver/transformer canônico e acompanha os caminhos reais de dependências/pacotes ligados de outro checkout. Não há alteração rastreada de `metro.config.js`. O transformer CSS usa a dependência opcional fixada `lightningcss-linux-x64-gnu@1.31.1`, preparada somente no `node_modules` ignorado desta bancada; o helper adiciona esse diretório ao `NODE_PATH` do processo de build sem editar o cache compartilhado.

## Estado de validação nesta preparação

- Resolver UI: 3/3. Uma mutação que escolhe arbitrariamente o primeiro vínculo fez o cenário ambíguo falhar (1 falha / 2 passes); fonte restaurada. O primeiro RED por arquivo ausente não é apresentado como RED comportamental.
- Typecheck web e build administrado: passaram antes da execução composta; o aviso de chunks grandes permanece.
- Typecheck normal Happier: terminou com saída 1 sem diagnóstico TypeScript; não é PASS. A checagem prévia R3 do mesmo menu (antes do identificador final de teste) permanece histórica.
- As primeiras exportações falharam por caminhos simbólicos Metro não acompanhados; a terceira atingiu o limite inicial de 240 segundos; a exportação seguinte chegou a 14.663 módulos e identificou mais um caminho real de pacote faltante. Logs negativos preservados. O setup também teve uma compilação local sem o flag administrado, corrigida antes do percurso final.
- O primeiro export completo em modo `--dev` gerou uma página vazia: chunks apenas com definições de módulos, nenhum bootstrap e metadata vazio. O screenshot e o JSON de falha estão preservados. Esse modo veio do helper WIP e foi removido; o comando corrente segue o `expo export --platform web --output-dir ...` usado pelos scripts canônicos de build da aplicação.
- Prova composta do autor: **PASS, exit 0**, com menu canônico real, painel autenticado no projeto diferente do padrão, política assinada publicada como revisão 2 (`maxProgrammersPerContext=2`) e conferida no PostgreSQL, ausência de prova humana recusada por `HUMAN_CONTROL_AUTH_REQUIRED`/403 com origem correta, pausa assinada e persistência após reload. `caller-proof.json` tem zero erros de página; screenshots mostram o menu e o painel. A revisão independente ainda é necessária para o aceite de RF-36.
- Export normal completo: 919 arquivos, árvore Happier `415b5303b2714abf60525361532264d7104d3bf3`; manifesto SHA-256 `49d722683eea84548c3783aedf920c390966075d2894a972a8b95dd0e887b748`. O manifesto versionado não contém credenciais. O artefato de runtime está em `/tmp/ac-r4-conversation-canonical-export`; conta, PG e processos do autor foram encerrados pelo runner, que terminou exit 0.
- Após a prova do autor, o helper recebeu guard explícito de WebSocket loopback, além do guard HTTP já executado, e o relatório emitido pelo runner passou a incluir IDs de projeto padrão/selecionado e o código exato da recusa. A revisão independente executa essa versão; a evidência do autor não é apresentada como reexecução dessas duas precisões do harness.

A compilação local inicial escreveu por engano no `web/dist` ignorado compartilhado por meio de um link próprio; gerência e frente UI foram avisadas, e o destino desta bancada passou a ser uma cópia isolada antes dos builds seguintes. Nenhum arquivo rastreado compartilhado foi alterado por esse erro.
