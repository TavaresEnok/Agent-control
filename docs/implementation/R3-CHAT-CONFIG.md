# R3 — configuração assinada pelo chat (RF-36)

O endpoint canônico Happier registra `agent-control.configure` em cada sessão criada por `happierEndpointFactory`, inclusive em `transportOnly`. Recebe envelope criptografado `{command, proof}`: `command` usa exatamente `ControlCommand`; `proof` usa exatamente `OperatorProof`, a mesma assinatura Ed25519 do painel. Não interpreta texto, não chama modelo e não cria prova a partir da chave de conteúdo da sessão.

`chatConfigurationHandler` chama o mesmo `Control.execute` que `/api/v1/ac/control`. O binding confiável do endpoint inclui principal, contexto, sessão, epoch/instância do gerente e fingerprint/versão/variante da chave. Dentro da mesma transação PostgreSQL do efeito, `Control.execute` confere RBAC, fence do gerente, link sessão/principal e chave ativa com locks, antes de verificar a assinatura humana e aplicar o dedupe existente. Não basta validar o endpoint antes da transação. Requisições de chat não escolhem esse binding.

O bootstrap `transportOnly` continua sem execução de tarefa ou inferência. Configuração humana tipada e assinada fica disponível; as regras já existentes de admission, revisão CAS e privilégios administrativos continuam aplicadas pelo mesmo serviço. O factory aceita `configurationControl` para injetar uma instância com os mesmos adapters e serviço administrativo do painel; o bootstrap deve passar a mesma instância para `startConfiguredManagerTransport` (quarto argumento) e `createApi` (décimo quarto, após quotaRegistry). O teste usa adapter sintético configurado e confirma `provider.bind` pelo chat com replay pelo painel; o probe não é executado.

## Validação física

`PATH=/tmp/node-v22.23.3-linux-x64/bin:$PATH node scripts/r3-chat-config-lab.mjs` passou com um teste, zero skips, em PostgreSQL e Happier light novos, portas loopback e HOME/SQLite temporários. O fixture usa protocolo RPC e criptografia reais do Happier, autentica conta sintética por desafio assinado e chama o painel por HTTP com token validado no Happier. Não usa conta preexistente nem API paga. A aplicação Cezar é instanciada e o gerente opera somente transporte; não se afirma prova de DAG nem execução de provedores.

A configuração pelo chat foi repetida pelo painel e a configuração pelo painel foi repetida pelo chat, com mesmo resultado e somente três intents duráveis (duas configurações de capacidade e um binding de adapter). Parada/reinício do endpoint preservou replay sem novo efeito. Foram recusados texto sem contrato, ausência de proof, payload adulterado com assinatura anterior, comando de outro contexto e execução normal de tarefa em `transportOnly`. Contraprovas chamando o handler diretamente, para não depender só do pré-check do endpoint, recusaram chave revogada, link trocado e gerente expirado; capacidade permaneceu na última revisão autorizada.

`npm run typecheck` normal passou, sem `skipLibCheck`. Dependências ignoradas foram ligadas somente onde ausentes, por manifesto privado do helper existente; o dist Cezar e suas dependências foram ligados ao cache já existente, sem reconstruir ou modificar o cache. A prova TAP pública está em `docs/validation/evidence/r3-chat-config-20261105.log`. O runner remove seu processo Happier e somente seu projeto Docker PostgreSQL com volumes. Recursos e credenciais operacionais não foram alterados.
